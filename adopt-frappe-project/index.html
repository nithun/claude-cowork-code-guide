    Adopt it for a new Frappe app

    Most TAP projects are Frappe (v15 on PostgreSQL). When your new project is also Frappe, you don't start the agent layer from a blank slate — you reuse the Frappe layer that already exists here. This is the Frappe-specific companion to Adopt it for a new project.

    What's reusable across any Frappe project

    Three things lift straight over — they're about Frappe, not about TAP's domain:

    1. The eight frappe-* skills (reference) — DocType, controller, client-script, hooks, api, postgres, test, bench. Copy skills/frappe-* into your new repo unchanged.
    2. The generic Frappe/Postgres rules baked into feature-builder, code-reviewer, test-runner — no ROW_COUNT(), the multi-value filter form, idempotent migrations, _()/__() translations, tests-in-the-same-commit, and the DocType-JSON-and-code-in-one-commit rule.
    3. Everything from the generic methodology — the two-tool model, doc-driven handoffs, the memory + retrospective loop.

    What you DON'T bring over

    TAP-domain rules are about this product, not Frappe — leave them behind:

    • Glific contact-field bundles, the SP state machine (T0–T25), Vocallabs parent calls.
    • The TAP-specific lessons in .claude/memory/lessons.md (the L-0xx rules about Glific / SP / Vocallabs).
    • app/, docs/architecture.md, TAP CRs / ADRs / PRDs.

    The line: a rule about how Frappe or Postgres behaves → keep it. A rule about how TAP's program works → drop it.

    How to set it up

    You still run the four bootstrap prompts (cowork-bootstrap.md), but you seed them with the Frappe layer so the generated agents are Frappe-aware from line one:

    1. Copy the skills in first: bash mkdir -p skills cp -r <claude-cowork-code>/skills/frappe-* skills/
    2. Run Prompt 0 (discovery). It detects Frappe (the apps/<name> layout, bench) and flags that Frappe runs from a separate bench location — so you'll symlink your app into the project folder, the same as TAP's app/.
    3. Run Prompt 1 (scaffold), telling it the frappe-* skills are already in skills/. The generated feature-builder / code-reviewer / test-runner will reference them and bake in the Postgres rules.
    4. Prompts 2–3 (retrospective + seed/verify) as normal — but seed lessons from your git history. Start with an empty Frappe-on-Postgres lesson set, not TAP's.

    Frappe-on-Postgres gotcha

    If your new app uses PostgreSQL (like TAP), the Postgres skill is the most important file you copy — most Frappe docs assume MariaDB, and the differences (quoting, ROW_COUNT(), JSON casts, migration patch SQL) cause silent bugs. If it uses MariaDB instead, drop frappe-postgres and let Prompt 0 note the difference.

    Checklist

    • [ ] skills/frappe-* copied into the new repo.
    • [ ] Prompt 0 detected Frappe + flagged the bench symlink.
    • [ ] Generated build agents reference the frappe skills + the Postgres rules.
    • [ ] Memory seeded from your history — no TAP-domain lessons carried over.
    • [ ] The bench symlink is wired (your app ↔ project folder), per SETUP.md.

    Then drive it with the engineering playbook.
