    Publishing the guide

    How this handbook gets to a public GitHub Pages site while the source repo stays private.

    The model: private source, public render

    claude-cowork-code is a private repo. GitHub Pages can't serve a private site on the current plan, so we don't try. Instead — exactly as the tap-lms-docs site already works — we render the Markdown and push only the built HTML to a separate public repo, whose Pages serves it.

    guide/  (private repo)  --mkdocs build-->  HTML  --gh-deploy-->  public docs repo (gh-pages)  -->  Pages URL

    Your private source, history, and the rest of the repo never leave the private repo. Only the rendered guide is public.

    What goes public

    This is a separate site from the TAP-LMS product docs (mkdocs.yml → published/). The guide site is configured by mkdocs-guide.yml with docs_dir: guide — so only files under guide/ are published. Nothing else in the repo is rendered.

    Keep guide/ generic. It's the public face: no credentials, no internal hostnames, no TAP-LMS internals beyond what's already labelled as examples. The docs_dir: guide boundary is your allowlist — anything you don't want public simply doesn't go in guide/.

    First-time setup (once)

    1. Create a public docs repo. Either in the org (e.g. theapprenticeproject/claude-cowork-code-guide) or a public personal repo. This repo holds only the rendered output.

    2. Add it as a git remote named guide-site: bash git remote add guide-site https://github.com/<owner>/<public-docs-repo>.git

    3. Ensure the docs venv exists (shared with the tap-lms-docs site): bash python3 -m venv .docs-venv .docs-venv/bin/pip install mkdocs-material

    4. Publish: bash ./scripts/publish-guide.sh It builds guide/ with --strict, shows you the target remote, asks for confirmation (the push is public and hard to undo), then gh-deploys to the gh-pages branch of guide-site.

    5. Enable Pages on the public repo: Settings → Pages → Source = gh-pages branch. The URL appears there (e.g. https://<owner>.github.io/<public-docs-repo>/).

    6. Record the URL in README.md and guide/index.md where they say "set after first deploy".

    Routine publish

    After the one-time setup, every update is one command:

    ./scripts/publish-guide.sh

    The gh CLI must be authed as an account with push access to the public repo (here, nithun). Run gh auth status to check.

    Adding or changing pages

    • Drop a new .md into guide/ — it appears in the menu automatically (the config has no nav: block; the menu is built from the files). Add a curated nav: to mkdocs-guide.yml later if you want titles/ordering.
    • Cross-link with relative .md paths ([Methodology](methodology.md)) — mkdocs rewrites them to the right URLs. The same links also work when browsing guide/ directly on GitHub.
    • Re-run ./scripts/publish-guide.sh to push the update.

    Why two sites, not one

    The TAP-LMS product docs and this methodology guide have different audiences and different public-vs-internal boundaries. Keeping them as two mkdocs configs (mkdocs.yml and mkdocs-guide.yml) with two site_dirs (site/ and site-guide/) means publishing one never touches the other.
