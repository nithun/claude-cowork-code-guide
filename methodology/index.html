    Methodology — why it's built this way

    The agents and skills change per project. These principles don't. Understanding them is what lets you drive the system instead of just typing at it.

    The problem this solves

    An LLM building software on its own tends to: lose context between sessions, repeat mistakes it already made, and blur planning into building until nobody can tell what was decided versus improvised. This system is six principles that fight each of those.

    1. Two tools, one folder

    Cowork plans. Claude Code builds. They share one folder and never write the same file at the same time.

    Planning (specs, CRs, reviews) and building (code, tests) are different modes of thought, and interleaving them is how half-built ideas get shipped. Splitting them across two tools — one without a terminal — makes the boundary physical. Work flows plan → build → review, sequentially.

    2. Documents are the interface

    Handoffs travel through named files in docs/, never through chat memory:

    • PRD — the what & why of a new feature.
    • BR — a bug report for a non-trivial defect.
    • CR — a scoped change to existing behavior. Immutable once approved — append-only after.
    • ADR — an architecture decision, with its trade-offs, recorded forever.

    A document is reviewable, diffable, and survives the session. Chat doesn't. "Implement CR-012" works tomorrow, on another machine, for another person — because CR-012 is a file. This is also what lets the Cowork↔Code boundary exist at all: the tools don't share memory, but they share the folder.

    3. One agent per step

    Eight narrow roles instead of one do-everything agent. Each does a single job well and hands off:

    prd-author → (architecture-reviewer?) → task-manager → feature-builder → code-reviewer + test-runner
change-requirement → (architecture-reviewer?) → feature-builder → code-reviewer + test-runner
                                                                          ↓ (recurring issue)
                                                                    retrospective

    Narrow agents are easier to trust, easier to review, and easier to regenerate for a new stack. A wide agent hides its reasoning; a narrow one's output is a checkable artifact.

    4. INVARIANTS — constraints that can't be self-edited

    Every agent file has a fenced ## INVARIANTS (do not edit) block listing its core job and the rules it must never weaken — even when the system is editing itself. The retrospective agent (principle 5) can rewrite skills and agents, but it is forbidden from touching anything inside an INVARIANTS fence, including its own. To change an invariant, it files a task for a human.

    This is the safety rail that makes self-improvement safe: the system can get smarter without being able to remove its own guardrails.

    5. Memory that compounds

    The system remembers, in .claude/memory/:

    • lessons.md — load-bearing rules. Append-and-supersede only: a rule is never reworded or deleted; a wrong one is marked superseded with a pointer (ADR-style), so the history of why survives.
    • patterns.md — canonical code idioms to reuse instead of reinventing.
    • Append logs — code-review findings, test failures, decisions.

    The retrospective agent reads all of it plus recent git history, finds patterns (a mistake that recurs ≥3 times, or one high-consequence bug), and turns each into a one-line rule that prevents the next occurrence. It audits its own past edits, too — a rule that didn't actually reduce the problem it targeted gets flagged.

    Two safety dials:

    • Autonomy — start proposal-only (it suggests; you apply). Graduate to closed-loop (it auto-applies, git is the rollback) once proposals are consistently good.
    • Circuit breaker — lanes (skills, agents, memory) that can be paused. A closed lane blocks writes there until a human reopens it.

    This is the compounding part: each recurring mistake becomes a rule, so the project gets more correct over time instead of drifting.

    6. Build the minimum, prove it, then expand

    Tooling follows the same MVP discipline as features: build only what the current work needs; expand because a measurement failed or a real need showed up, never because building has momentum. TAP LMS started single-tier memory and deferred a second tier, deferred a weekly cron, and kept deployment manual — each revisited only when evidence demanded. Apply the same restraint to your own layer: don't add an agent, a memory tier, or a skill until the work asks for it.

    The payoff

    Plan and build stop colliding (1, 2). Decisions become durable and reviewable (2). Each step is a checkable artifact (3). The system can improve itself without removing its guardrails (4, 5). And it stays small until evidence says otherwise (6).

    The result: a build loop that closes itself — write the spec, build it, review and test it, learn from it — and gets more correct the longer you run it.
