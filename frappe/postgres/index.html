    Frappe + PostgreSQL skill

    Frappe was born MariaDB-first; Postgres support landed later and is fully functional but riddled with small differences. Most Frappe code runs the same; raw SQL and a handful of operations don't.

    Quick rule

    Whenever you write SQL, ask: would this work on Postgres? Most copy-pasted Frappe ERPNext SQL was written against MariaDB and will quietly fail or behave differently on PG.

    The differences that bite

    Identifier quoting

    MariaDB uses backticks: `tabCourse`. Postgres uses double quotes: "tabCourse". Frappe's frappe.db.sql translates backticks at runtime, but only inside the bare query string — not inside dynamically built fragments or stored procedures. If you see psycopg2.errors.SyntaxError: syntax error at or near ""`, that's a backtick that didn't get translated.

    Safer: write idiomatic Postgres SQL with "..." quoting and let frappe.db.sql pass it through, OR use the query builder (frappe.qb) which is dialect-aware.

    IFNULL / ISNULL → COALESCE

    -- Bad on PG
SELECT IFNULL(grade, 0) FROM "tabAttempt";
-- Good
SELECT COALESCE(grade, 0) FROM "tabAttempt";

    GROUP_CONCAT → STRING_AGG

    -- MariaDB
SELECT GROUP_CONCAT(student SEPARATOR ', ') FROM "tabCourse Enrollment";
-- Postgres
SELECT STRING_AGG(student, ', ') FROM "tabCourse Enrollment";

    Date math

    DATE_ADD(d, INTERVAL 1 DAY) is MariaDB. PG: d + INTERVAL '1 day' or d + 1 for date types. DATEDIFF(a, b) becomes (a::date - b::date). NOW() works both places; CURDATE() is MariaDB-only — use CURRENT_DATE.

    LIMIT x, y → LIMIT y OFFSET x

    PG doesn't accept the two-argument form.

    Case sensitivity

    PG is case-sensitive on identifiers and on string comparisons. WHERE email = 'Foo@Bar.com' won't match foo@bar.com rows. Use ILIKE or LOWER(email) = LOWER(...) and put a functional index on LOWER(email) if you query that way.

    Boolean

    PG has a real BOOLEAN type; MariaDB uses TINYINT(1). Frappe's Check field maps to int on both — your queries should compare flag = 1, not flag = TRUE, to stay portable.

    SELECT ROW_COUNT() does not exist on PG

    MariaDB has a session-level ROW_COUNT() you can SELECT after an UPDATE/DELETE to count affected rows. Postgres does not — that query errors out (or, worse on Frappe, returns nothing useful). Two correct alternatives:

    # Option A — RETURNING (preferred for UPDATE-claim patterns)
claimed = frappe.db.sql("""
    UPDATE "tabProgramEnrollment"
       SET journey_label = %s
     WHERE name = %s AND journey_label = %s
     RETURNING name
""", (new_label, pe_name, expected_label))
if not claimed:
    return  # 0 rows = somebody else already moved it

# Option B — cursor.rowcount when RETURNING isn't ergonomic
n = frappe.db.sql("UPDATE ... WHERE ...", values)
# frappe.db._cursor.rowcount has the count; usually you want RETURNING instead.

    Lesson L-001. Single highest-consequence MariaDB-ism on this project — silently broke an atomic claim in production-bound code (CR-2026-05-10 #B1). When you see SELECT ROW_COUNT() in any patch or controller, treat it as BLOCKING.

    WHERE col IN %s → WHERE col = ANY(%s) (and the Frappe modify_values gotcha)

    The IN %s form with a tuple parameter is a MariaDB/psycopg trick that doesn't always survive on PG (and will silently behave wrong on empty tuples). Use = ANY(%s) with a Python list for portable, robust PG SQL:

    # Bad
frappe.db.sql("SELECT name FROM \"tabFoo\" WHERE state IN %s", (("a", "b", "c"),))

# Good
frappe.db.sql("SELECT name FROM \"tabFoo\" WHERE state = ANY(%s)", (["a", "b", "c"],))

    Lesson L-005.

    Common second-order trap (recurred 3× — pe_dispatcher → migration patch → next patch): Frappe's frappe.db.sql runs the params through modify_values(), which wraps a single-item (list,) tuple oddly. If you write frappe.db.sql("... = ANY(%s::text[])", (legacy_names,)) you'll get op ANY/ALL (array) requires array on right side or malformed array literal at runtime — the tuple-around-list becomes a Postgres composite, not an array. Pick one of these two safe forms and don't mix them:

    # Form A — `= ANY(%s)` with a bare list (NOT a tuple wrapping a list)
frappe.db.sql(
    'SELECT name FROM "tabFoo" WHERE state = ANY(%s)',
    ([s for s in states],),       # ← this is the one place the (list,) wrapping is correct
)
# Note: psycopg2 needs the outer tuple as the params iterable. The inner is the actual list.
# In practice, prefer Form B for migration patches — it avoids the cognitive load.

# Form B — `IN %s` with `tuple(list)` (Frappe's canonical Postgres-safe pattern)
frappe.db.sql(
    'UPDATE "tabPGCollection" SET is_active = 0 WHERE parent IN %s',
    (tuple(legacy_bpr_names),),
)

    The recurrence (CR-2026-05-15 C1, fixed in commit 561bb5c) was specifically a migration patch that copied the = ANY(%s::text[]) shape from an in-line comment but passed (list,) and got the modify_values mangling. Code-reviewer rule: whenever you see ANY(%s) or ANY(%s::text[]) in raw SQL, immediately check the param shape — if it's (some_list,) where some_list is a Python list of strings/ints, it will fail at runtime. Prefer IN %s + tuple(list) for migration patches.

    ON DUPLICATE KEY UPDATE → ON CONFLICT

    -- PG upsert
INSERT INTO "tabLesson Progress" (name, status)
VALUES (%s, %s)
ON CONFLICT (name) DO UPDATE SET status = EXCLUDED.status;

    Full-text search

    Frappe's LIKE '%foo%' works but is slow. PG has to_tsvector / to_tsquery and GIN indexes — much faster for text search. Frappe's global search uses its own table (__global_search) and works the same on either backend, so prefer it over hand-rolled LIKE queries when possible.

    JSON fields

    Frappe JSON fieldtype is stored as text historically, not jsonb. If you need to query into JSON values, you currently have to cast: (value::jsonb->>'key'). Add a generated column or a separate indexed column if you query the same JSON path repeatedly.

    If you want a GIN index on the JSON (for @>, ?, key-existence queries), the column itself must be real jsonb, not text. Convert via patch:

    def execute():
    frappe.db.sql_ddl("""
        ALTER TABLE "tabProgramEventLog"
        ALTER COLUMN details TYPE jsonb USING details::jsonb;
    """)
    frappe.db.sql_ddl("""
        CREATE INDEX IF NOT EXISTS idx_eventlog_details
        ON "tabProgramEventLog" USING GIN (details);
    """)

    Lesson L-006. Without the USING details::jsonb cast clause, ALTER fails on rows with non-trivial content.

    Postgres string functions on JSON columns need an explicit ::text cast

    -- WORKS
SELECT LEFT(details::text, 200) FROM "tabProgramEventLog";
SELECT * FROM "tabError Log" WHERE error::text LIKE '%foo%';

-- FAILS — `function left(json, integer) does not exist`
SELECT LEFT(details, 200) FROM "tabProgramEventLog";
SELECT * FROM "tabError Log" WHERE error LIKE '%foo%';

    Affects ProgramEventLog.details, Submission.feedback, Error Log.error, and any column declared as Code (JSON) in DocType JSON. Lesson L-051.

    Frappe column-name surprises (no consistent mapping from field label to DB column)

    DocType Field label / what you think it's called Real Postgres column Notes
    Error Log "Title" / what log_error(title=...) takes method The kwarg is title=, the column is method. Both are correct — Frappe maps title→method internally. Query with WHERE method LIKE 'SP %'.
    Error Log "Error" / "Message" / the long body error Not message. And it's JSON-typed (see above).
    ProgramEventLog The PE foreign key enrollment NOT program_enrollment despite the convention used elsewhere. Hit during 2026-05-26 diagnostics.

    Rule: when raw SQL against a Frappe doctype errors with column "X" does not exist, do NOT assume the field is misnamed — check the actual schema first:

    SELECT column_name FROM information_schema.columns
 WHERE table_name = 'tabError Log' AND table_schema = 'public'
 ORDER BY ordinal_position;

    A failed query poisons the transaction until you call frappe.db.rollback()

    Unlike MariaDB (autocommits) PG enters an aborted-transaction state on the first failed statement. EVERY subsequent statement in the same txn errors with InFailedSqlTransaction: current transaction is aborted, commands ignored until end of transaction block. Two implications:

    1. In bench console, wrap risky probes or start each cell with frappe.db.rollback(). The corollary is that sp_console helpers all begin with that call.
    2. In exception handlers that call frappe.log_error, rollback BEFORE log_error. frappe.log_error does its own SELECT to fetch the Error Log doctype meta; without the rollback that SELECT itself fails and you lose the entire error report.
    try:
    frappe.db.sql("...risky SQL...")
except Exception as e:
    try:
        frappe.db.rollback()    # ← clear the poisoned txn FIRST
    except Exception:
        pass
    frappe.log_error(f"failed: {e}", "My App")    # now this actually works
    raise   # in an RQ job, ALWAYS re-raise (see frappe-hooks skill)

    Lesson L-030. Documented in CLAUDE.md as a project-level gotcha.

    Console writes need an explicit frappe.db.commit() to persist

    IPython console runs everything in one implicit transaction. If a later cell errors and you call frappe.db.rollback(), all uncommitted writes from EARLIER cells (including frappe.log_error inserts and frappe.db.set_value updates) get wiped along with the poisoned txn. After diagnostics that depend on side effects (event log entries, prospect_id cache writes), call frappe.db.commit() before any subsequent query that could fail.

    Use the query builder when you can

    frappe.qb (PyPika under the hood) emits dialect-correct SQL for both backends:

    from frappe.query_builder import DocType
from frappe.query_builder.functions import Coalesce, Count

Enrollment = DocType("Course Enrollment")
Course = DocType("Course")

q = (
    frappe.qb.from_(Enrollment)
    .left_join(Course).on(Enrollment.course == Course.name)
    .select(Course.title, Count(Enrollment.name).as_("enrollments"))
    .where(Enrollment.status == "Active")
    .groupby(Course.title)
    .orderby(Count(Enrollment.name), order=frappe.qb.desc)
)
rows = q.run(as_dict=True)

    This is the strongly-recommended default for non-trivial queries.

    Indexes

    Frappe creates indexes on Link fields and on fields with index: 1 in the JSON. After adding index: 1, run bench migrate — Frappe will issue CREATE INDEX against PG.

    For composite indexes or partial indexes (PG-only feature, very useful), use a patch:

    # app/<your_app>/patches/v1_0/add_active_enrollment_index.py
import frappe

def execute():
    frappe.db.sql_ddl(
        'CREATE INDEX IF NOT EXISTS idx_active_enrollment '
        'ON "tabCourse Enrollment" (student, course) '
        'WHERE status = \'Active\';'
    )

    Register the patch in app/<your_app>/patches.txt so bench migrate picks it up.

    Migrations & schema sync

    bench migrate runs frappe.model.sync.sync_for("<app>") which diffs the DocType JSON against the live PG schema and issues ALTER TABLE statements. Watch for:

    • Renaming a field doesn't auto-rename the column. You need a patch that runs frappe.db.rename_column (or hand-rolled ALTER TABLE ... RENAME COLUMN).
    • Changing a field's fieldtype may require a USING clause for PG to coerce existing data. Frappe tries; sometimes you must intervene.
    • Dropping a field doesn't drop the column by default — Frappe leaves it for safety. Use DROP COLUMN in a patch if you really want it gone.

    Migration co-authoring — three artifacts must agree

    When you add a new column to a doctype, three artifacts must be edited in the same change set. Edit two but not the third and bench migrate fails at the worst possible moment (production deploy, freshly cloned site, CI restore). The CR-005 PGCollection.kind incident shipped broken twice (2026-05-15) because of this exact mismatch.

    Artifact What it controls
    <doctype>.json Whether the column exists in the schema after bench migrate
    Patch in patches/v0_X/*.py What backfill / SQL writes run against the new column
    patches.txt The ORDERING — whether the patch runs pre or post [post_model_sync]

    Hard rules

    1. Every patch that references a new column should call frappe.reload_doc("<app>", "doctype", "<doctype>") at the top. This forces the DocType JSON to apply (creating the column if missing) BEFORE the patch body runs. Idempotent and cheap. See app/tap_lms/patches/v0_2/backfill_pg_collection_kinds.py and app/tap_lms/patches/v0_2/add_pe_glific_id_unique_index.py for the canonical pattern.

    2. frappe.db.rollback() at the very top of every patch. Clears any poisoned transaction state from earlier patches in the chain. Without this, a single upstream failure cascades through every subsequent patch with current transaction is aborted, commands ignored until end of transaction block.

    3. Use IF NOT EXISTS on every CREATE INDEX / CREATE TABLE. Patches are idempotent by Frappe convention (L-021) — re-running on a partially- migrated DB must be a no-op, never a "duplicate object" error.

    Canonical patch skeleton

    """
<purpose, 1-3 lines>
"""
import frappe


def execute():
    # PG txn hygiene — clear any poisoned txn state from prior patches.
    frappe.db.rollback()

    # Self-heal: force the doctype JSON to sync so columns we reference
    # are guaranteed live before our SQL runs. Idempotent + cheap.
    frappe.reload_doc("tap_lms", "doctype", "<doctype>")

    # Actual migration work — use IF NOT EXISTS for DDL idempotency.
    frappe.db.sql("""
        CREATE UNIQUE INDEX IF NOT EXISTS idx_foo
            ON "tabBar" (some_col)
         WHERE some_col IS NOT NULL
    """)
    frappe.db.commit()

    frappe.logger().info("patch_foo: ...")

    patches.txt — section headers are mandatory (L-058)

    Frappe's patch loader uses configparser to read patches.txt and runs two distinct phases:

    1. pre_model_sync — patches that need to run BEFORE the doctype sync (rare; mostly for cleanup that the schema sync would otherwise stumble on)
    2. sync_doctypes() — creates/alters all doctype tables
    3. post_model_sync — patches that need to run AFTER the tables exist (the common case for tap_lms — every patch references SP doctype tables)

    Required shape — both section headers, even if one is empty:

    [pre_model_sync]

[post_model_sync]
tap_lms.patches.cr_004_scale.idx_pe_next_action
tap_lms.patches.cr_004_batch_id_unique.batch_id_unique_constraint
tap_lms.patches.v0_2.backfill_pg_collection_kinds
...

    Common failure modes:

    If patches.txt has... Frappe behavior
    No section headers at all All patches default to pre_model_sync → run BEFORE tables exist → fail with UndefinedTable on fresh installs
    Only [post_model_sync] Loader queries [pre_model_sync] first, can't find it → ValidationError: Patch type PatchType.pre_model_sync not found in patches.txt
    Only [pre_model_sync] Same as above but mirrored — fails when post_model_sync query happens
    Both headers, empty pre_model_sync ✅ Works
    Both headers populated correctly ✅ Works

    We hit this on 2026-05-30 during the prod first-install. On migration deploys the bug is invisible because the tables already exist from earlier migrates; on fresh installs every patch fails.

    Patches reading from dropped legacy columns need has_column guards (L-059)

    When a CR drops a column from a doctype's JSON AND the same CR includes a backfill patch that reads from that column for the migration path, the patch must guard the read:

    def execute():
    # On migration deploys, the legacy column still exists in PG
    # (Frappe doesn't auto-drop columns when a field is removed from JSON).
    # On fresh installs, the column was never created.
    if frappe.db.has_column("tabEscalationStep", "message_type"):
        backfilled = frappe.db.sql("""
            UPDATE "tabEscalationStep"
               SET escalation_type = CASE
                       WHEN message_type = 'help_note_a' THEN 'help_note_a'
                       ...
                   END
             WHERE escalation_type IS NULL OR escalation_type = ''
            RETURNING name
        """)
        backfill_count = len(backfilled or [])
    else:
        backfill_count = 0   # fresh install — nothing to backfill

    Without the guard, the patch fails on fresh installs with psycopg2.errors.UndefinedColumn: column "message_type" does not exist.

    Hit 2026-05-30 in cr_003.per_week_grace_and_channels Step 1 against tabEscalationStep.message_type. The patch was unblocked by manually inserting a Patch Log entry (Step 1 was a no-op on the empty fresh table anyway); the source-tree fix added the guard.

    Reviewer rule

    When reviewing a new patch, verify: - [ ] frappe.db.rollback() at the top - [ ] frappe.reload_doc(...) if any column referenced is newly added - [ ] IF NOT EXISTS on all CREATE statements - [ ] Idempotent on re-run (no errors, no duplicate side effects) - [ ] Listed in patches.txt under [post_model_sync] (not above any header) - [ ] patches.txt has BOTH [pre_model_sync] and [post_model_sync] section headers (L-058) - [ ] Reads from LEGACY columns (being dropped in the same CR) are guarded with frappe.db.has_column(table, col) (L-059) - [ ] DocType JSON has the column the patch reads/writes — if not, the patch is shipping ahead of the schema and will fail on a fresh install

    Backups and restore

    # Backup
bench --site <site> backup --with-files
# This produces SQL dumps via pg_dump under the hood.

# Manual backup of just the DB
pg_dump -U <db_user> -h 127.0.0.1 -d <db_name> -F c -f /tmp/site.dump

# Restore
pg_restore -U <db_user> -h 127.0.0.1 -d <db_name> --clean /tmp/site.dump

    bench restore <sql_path> works for .sql.gz dumps produced by Frappe; if you've taken a custom pg_dump, restore with pg_restore directly.

    Connection tuning

    In common_site_config.json:

    {
  "db_type": "postgres",
  "db_host": "127.0.0.1",
  "db_port": 5432,
  "rds_db": 0
}

    Per-site DB credentials in sites/<site>/site_config.json. Production: bump max_connections (PG default 100 is too low if you run multiple workers + gunicorn) and ensure shared_buffers is at least 25% of RAM.

    Locking

    Frappe acquires advisory locks via frappe.db.get_value(..., for_update=True) which translates to SELECT ... FOR UPDATE. Hold these locks for as little time as possible — in PG, a long-held row lock can block migrations and other writers.

    FOR UPDATE SKIP LOCKED for parallel workers

    PG-specific (not in MariaDB until 8.0+, and even there with caveats). The right primitive for parallel scheduler tick handlers that want to grab the next batch without blocking on rows another worker already holds:

    SELECT name, next_action_type, journey_label
  FROM "tabProgramEnrollment"
 WHERE next_action_at <= NOW()
   AND next_action_at IS NOT NULL
   AND program_status = 'active'
 ORDER BY next_action_at
 LIMIT 1000
 FOR UPDATE SKIP LOCKED;

    Lesson L-003. See also pattern P-003 (per-PE event-driven scheduler tick) for the full shape.

    The atomic-claim pattern (project canonical)

    Every state-changing UPDATE on ProgramEnrollment (or any state-machine doc) must include a WHERE journey_label = expected_label guard plus RETURNING name, and check the result. 0 rows returned = a parallel handler already moved the state, skip gracefully. This is the project's idempotency primitive — pattern P-001 in .claude/memory/patterns.md.

    claimed = frappe.db.sql("""
    UPDATE "tabProgramEnrollment"
       SET resolved_flow_state = %s,
           journey_label       = %s,
           next_action_at      = %s,
           next_action_type    = %s
     WHERE name          = %s
       AND journey_label = %s         -- ← idempotency guard
     RETURNING name
""", (new_state, new_label, next_at, next_type, pe_name, expected_label))

if not claimed:
    return                    # parallel handler already moved state

    Anti-patterns to flag in review:

    • A broad except Exception: block wrapping the UPDATE with a "MariaDB fallback" branch — that's dead code on this PG-only project, swallows real errors, and risks double-running. Remove it (lesson L-007).
    • SELECT ROW_COUNT() instead of RETURNING — see above, L-001.
    • Using pe = frappe.get_doc(...); pe.field += x; pe.save() for fields that race against scheduler resets — use the COALESCE-update form (pattern P-002) instead.

    Race-tolerant counter updates

    For columns that can be reset (e.g., weekly_* fields T14 zeros out) or incremented from multiple handlers, never read-then-write. Use a single atomic UPDATE with COALESCE:

    UPDATE "tabProgramEnrollment"
   SET total_quiz_points  = COALESCE(total_quiz_points, 0)  + %s,
       weekly_quiz_points = COALESCE(weekly_quiz_points, 0) + %s
 WHERE name = %s

    Lesson L-011, pattern P-002.

    Vacuum and analyze

    PG's autovacuum handles most cases, but after a big migration or bulk import, run VACUUM ANALYZE on the affected tables manually to refresh statistics. The query planner uses these stats; stale stats produce sequential scans on tables that have indexes.

    psql -U <db_user> -d <db_name> -c 'VACUUM ANALYZE "tabCourse Enrollment";'

    Debugging slow queries

    EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;

    Look for Seq Scan on big tables — usually means a missing index or a planner issue. PG has a richer EXPLAIN output than MariaDB; learn to read it.

    Don't reach for these

    • Stored procedures and triggers in PG — Frappe's framework expects logic in Python controllers, not in the DB. You'll create maintenance pain and confuse the migration path.
    • pg_partman partitioning — works, but Frappe's ORM doesn't know about partitions and you'll get surprises in frappe.get_all.
    • Foreign key constraints beyond what Frappe creates — Frappe enforces relationships in Python, not at the DB level. Adding raw FKs can break delete operations.
