    Frappe DocType skill

    DocTypes are Frappe's data model. A DocType bundles together a database table, a form UI, server-side controller, and permissions in one declarative JSON file plus a sibling Python module.

    When to use which mechanism

    Three ways to extend the data model — pick correctly, this is where most Frappe projects go wrong.

    • New DocType in your custom app — for entities your app owns (e.g., Course Enrollment, Lesson Progress). Lives in app/<your_app>/<your_module>/doctype/<doctype_name>/. Editable by developers, version-controlled.
    • Custom Field on a core DocType — adds a single field to ERPNext-owned DocTypes (Customer, Item, User). Stored as Custom Field records, fixtures-exportable. Use when the field is conceptually "ours" but lives on a foreign DocType.
    • Customize Form / Property Setter — change properties of existing fields (label, reqd, hidden, default). Stored as Property Setter records. Don't use to add fields — that's Custom Field's job.

    If you're tempted to fork or directly edit a core DocType JSON, stop — it'll get blown away on next bench update. Use Custom Fields.

    Anatomy of a DocType folder

    <your_app>/<your_module>/doctype/course_enrollment/
├── __init__.py
├── course_enrollment.json     # schema + UI definition
├── course_enrollment.py       # controller (server-side)
├── course_enrollment.js       # client script (browser-side, optional)
├── test_course_enrollment.py  # unit tests
└── course_enrollment_dashboard.py  # dashboard config (optional)

    The naming is strict: snake_case folder + matching filenames. The name field inside the JSON is the human "Course Enrollment".

    Field types worth knowing

    Data (short text), Small Text / Long Text / Text Editor (rich), Int, Float, Currency, Percent, Date, Datetime, Time, Check (boolean), Select (dropdown with options newline-separated), Link (foreign key — options is the target DocType), Dynamic Link (target chosen at runtime via another field), Table (child table — options is child DocType), Table MultiSelect (many-to-many sugar), Attach / Attach Image, Code / JSON, Password (encrypted at rest), Geolocation, Color, Signature.

    For LMS-style work in TAP LMS, the common patterns are: Link to Course, Student, Instructor; Table for lesson lists, attempt logs, rubric rows; Select for status fields; Datetime for scheduling.

    Naming

    The naming_rule plus autoname field decide how new docs get their primary key. Pick one consciously:

    • field:<fieldname> — name = value of that field (must be unique). Good for human-meaningful names like course codes.
    • naming_series: plus a naming_series Select field — ENROLL-.YYYY.-.#### style. Best default for transactional records.
    • format: — Jinja-ish template, e.g. {course}-{student}.
    • Prompt — user types it.
    • Autoincrement — Postgres bigserial. Fast, opaque, no sortable meaning.
    • hash — random. Use for high-write-concurrency doctypes (see warning below); avoid otherwise if a meaningful name is cheap.

    For TAP LMS, prefer naming series for enrollments/attempts/progress (audit-friendly) and field: for catalog items like Course (uses course_code).

    Counter-autoname (format:...{####} / naming_series:) serializes concurrent inserts — never use it on a hot, webhook-driven doctype. Every {####} insert takes FOR UPDATE on the shared tabSeries.current row. Under concurrent Glific-webhook dispatch this produces psycopg2.errors.SerializationFailure: could not serialize access due to concurrent update, which then cascades via the L-030 poisoned-txn path into a Glific 400. The 2026-06-04 trainer-cohort incident (BR-003) hit this on StudentStageProgress insert from get_next_content. Fix: use hash autoname (no shared counter → contention disappears at the source) for any doctype inserted on the request path of a high-concurrency endpoint. Hash and format names coexist within one doctype, so converting is safe as long as nothing constructs or parses the .name (lookups must be by field filter or stored .name). See L-075.

    Permissions

    Edit permissions array directly in the JSON, or use the Role Permission Manager UI and export as fixture. Match each row to a Role, set read/write/create/delete/submit/cancel/amend flags, and set permlevel (0 = whole doc, higher levels = field-level locks via the field's permlevel).

    User Permissions further restrict by linked record (e.g., "this instructor only sees their own Courses") and are applied at runtime — set apply_user_permissions on relevant Link fields.

    Submittable vs not

    Setting is_submittable: 1 gives you the submit/cancel/amend lifecycle (docstatus 0=draft, 1=submitted, 2=cancelled). Use for accounting-shaped data where audit trail matters (attempts, certifications, payments). Don't use for plain CRUD records — adds friction with no upside.

    After every schema change

    The schema only goes live after bench --site <site> migrate. Without migrate, the form looks updated but the Postgres table is stale and writes will silently drop new fields. Always run migrate (or remind the user to) after editing a DocType JSON.

    Editing JSON safely

    Order matters less than you'd think — Frappe sorts field order from the idx value, not the array position. But: keep module, name, engine, creation untouched unless you know what you're doing. Don't hand-edit the modified timestamp; let Frappe rewrite it.

    When generating new DocType JSON, model it after one of the existing DocTypes in app/<your_app>/<your_module>/doctype/ — copy a sibling, then change name, fields, permissions. Frappe is finicky about the exact key names.

    Child tables

    A child DocType has istable: 1 and no permissions of its own — it inherits from the parent. The parent declares the relationship with a Table field whose options points at the child. Don't try to query a child table directly via frappe.get_all without filtering by parent and parenttype, or you'll get rows from every parent that uses this child type.

    Single DocType

    Setting issingle: 1 makes a settings-style record — exactly one row, addressed by name = DocType name (e.g., "TAP LMS Settings"). Stored in tabSingles as key/value rows, not as a regular table. Use for app-wide config.

    Reference: minimal JSON shape

    {
  "doctype": "DocType",
  "name": "Course Enrollment",
  "module": "TAP LMS",
  "engine": "InnoDB",
  "naming_rule": "By \"Naming Series\" field",
  "autoname": "naming_series:",
  "fields": [
    {"fieldname": "naming_series", "fieldtype": "Select", "label": "Series",
     "options": "ENROLL-.YYYY.-.#####", "reqd": 1},
    {"fieldname": "student", "fieldtype": "Link", "options": "Student", "reqd": 1, "in_list_view": 1},
    {"fieldname": "course", "fieldtype": "Link", "options": "Course", "reqd": 1, "in_list_view": 1},
    {"fieldname": "enrolled_on", "fieldtype": "Datetime", "default": "now"},
    {"fieldname": "status", "fieldtype": "Select", "options": "Active\nCompleted\nDropped", "default": "Active", "in_list_view": 1}
  ],
  "permissions": [
    {"role": "TAP Instructor", "read": 1, "write": 1, "create": 1, "delete": 0},
    {"role": "TAP Student", "read": 1}
  ]
}

    (Note engine: "InnoDB" is harmless on Postgres — Frappe keeps the field for compatibility.)

    Postgres caveat

    Frappe creates the table via its own migration code, not raw CREATE TABLE. Field name collisions with Postgres reserved words (e.g. user, order, group) will cause grief — Frappe quotes table names but not always inside ad-hoc joins. Avoid those names where possible; if forced, expect to debug an occasional psycopg2.errors.SyntaxError and consult the frappe-postgres skill.
