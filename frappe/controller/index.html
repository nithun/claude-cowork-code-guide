    Frappe controller skill

    The controller is <doctype>.py next to the DocType JSON. It defines a class that subclasses Document and exposes lifecycle methods Frappe calls automatically.

    Lifecycle order — memorize this

    For an insert: autoname → before_insert → validate → before_save → (DB INSERT) → after_insert → on_update

    For an update: validate → before_save → (DB UPDATE) → on_update

    For a submit: validate → before_save → (DB UPDATE) → on_update → before_submit → (set docstatus=1) → on_submit

    For a cancel: before_cancel → (set docstatus=2) → on_cancel → on_update_after_submit

    For a delete: on_trash → (DB DELETE) → after_delete

    Pick the right hook. validate is for guarding writes (raise if data is bad). on_update is for side effects that need the doc to already exist in DB (creating linked records, sending emails). before_save is rare — prefer validate.

    Skeleton

    import frappe
from frappe.model.document import Document
from frappe import _


class CourseEnrollment(Document):
    def validate(self):
        self._guard_duplicate_enrollment()
        self._set_default_status()

    def on_submit(self):
        self._notify_student()
        self._create_progress_record()

    def on_cancel(self):
        # Reverse anything on_submit did.
        frappe.db.set_value(
            "Lesson Progress",
            {"enrollment": self.name},
            "status", "Cancelled",
        )

    # --- private helpers -------------------------------------------

    def _guard_duplicate_enrollment(self):
        if frappe.db.exists(
            "Course Enrollment",
            {"student": self.student, "course": self.course, "name": ("!=", self.name)},
        ):
            frappe.throw(_("{0} is already enrolled in {1}").format(self.student, self.course))

    def _set_default_status(self):
        if not self.status:
            self.status = "Active"

    def _notify_student(self):
        # ...
        pass

    def _create_progress_record(self):
        # ...
        pass

    Use leading-underscore helpers to keep the public surface clean. Frappe only calls methods named after lifecycle events; everything else is yours.

    Raising errors the right way

    frappe.throw(_("message")) aborts the transaction and shows the message to the user. frappe.msgprint(_("...")) shows a non-fatal notice. Always wrap user-visible strings in _() for translation. Pass title and indicator for richer UX:

    frappe.throw(_("Course is full"), title=_("Cannot enrol"), indicator="red")

    Custom exception classes give cleaner programmatic handling:

    class CourseFullError(frappe.ValidationError): pass

frappe.throw(_("Course is full"), exc=CourseFullError)

    Reading and writing data

    Inside a controller, the doc itself is self. For other docs:

    • frappe.get_doc("Course", course_name) — full document object, fires controller hooks on save.
    • frappe.get_cached_doc(...) — same but cached for the request. Use for read-only lookups in hot paths.
    • frappe.db.get_value("Course", name, "title") — single-field read, no controller. Fast.
    • frappe.db.get_value("Course", {"code": "CS101"}, ["title", "credits"], as_dict=True) — filter + multi-field.
    • frappe.get_all("Course Enrollment", filters={"student": self.student}, fields=["name", "status"]) — multi-row read; respects user permissions if ignore_permissions not set.
    • frappe.db.sql("SELECT ...", values, as_dict=True) — escape hatch. Use parameterized queries; never f-string user input.
    • frappe.db.set_value("Course", name, "status", "Closed") — single-field write, does not fire controller hooks. Use sparingly; prefer loading the doc and calling .save() so validation runs.

    Permissions inside the controller

    Controllers run with the caller's permissions by default. To bypass (e.g., a student submission needs to update an instructor's record), pass ignore_permissions=True to .save() / .insert(), or run the work inside frappe.flags overrides. Be deliberate — bypassing is the #1 source of authorization bugs.

    note = frappe.new_doc("Communication")
note.subject = f"New enrollment from {self.student}"
note.insert(ignore_permissions=True)

    Transactions

    Each request runs in a single transaction; Frappe commits on success and rolls back on exception. Avoid manually calling frappe.db.commit() inside controller code — it breaks atomicity. The exceptions are background jobs and long migrations, where partial commits are intentional.

    Background work

    on_submit should not block the user for >100ms. Anything heavy (PDF rendering, external API calls, sending many emails) goes in frappe.enqueue:

    def on_submit(self):
    frappe.enqueue(
        "tap_lms.tap_lms.doctype.course_enrollment.course_enrollment.send_welcome_packet",
        enrollment=self.name,
        queue="long",
        job_name=f"welcome:{self.name}",
    )

    The function must be importable by dotted path (so module-level, not a method on self). Pass primitive args.

    Background jobs — log structured context on BOTH paths

    Background jobs (frappe.enqueue targets, scheduler functions) that swallow exceptions silently are the #1 source of "but the queue says success" debugging pain on this project. Filed as bugs #3 and #5 (both 2026-05-18): _process_pe_chunk silently rejected 4 of 41 PE creations and _sync_contact_fields_job intermittently dropped field writes — neither left an Error Log entry, both took hours of console diagnostics to find.

    Hard rule for any background job:

    1. Every try/except must log via frappe.log_error(title=..., message=...) with structured context: PE name, student ID, glific ID, batch name, the action that was attempted, the underlying exception type + message.
    2. The success path must log via frappe.logger().info(...) with at minimum "what worker ran, what entity, what changed." This is what lets ops answer "did this contact actually receive the field update?" without running custom diagnostic queries.
    3. Returning silently with no exception AND no log is BLOCKING per code reviewer. Workers must succeed visibly or fail visibly — not both, never neither.
    4. DLQ patterns (P-007 / L-015) make the silent-success case technically OK only if the success path itself logs as in (2).

    Wrong pattern

    def _sync_contact_fields_job(glific_id, fields, pe_name, ...):
    try:
        update_contact_fields(glific_id, fields)
    except Exception:
        pass   # ← BLOCKING: silent swallow

    Right pattern

    def _sync_contact_fields_job(glific_id, fields, pe_name, ...):
    try:
        update_contact_fields(glific_id, fields)
        frappe.logger().info(
            f"sync_contact_fields_ok: pe={pe_name} glific={glific_id} "
            f"fields_count={len(fields)}"
        )
    except Exception as e:
        frappe.log_error(
            title="SP Glific Sync Failed",
            message=(
                f"sync_contact_fields_failed: pe={pe_name} "
                f"glific={glific_id} fields={list(fields.keys())} "
                f"error={type(e).__name__}: {e}"
            ),
        )
        raise   # let the retry/DLQ machinery handle re-enqueue

    Use a structured log-key prefix (e.g. sync_contact_fields_ok / sync_contact_fields_failed) so ops can grep for either outcome.

    External identifier semantics — avoid contact_id ↔ student_id confusion

    The project carries multiple distinct kinds of identifiers that share variable names across functions. Confusing them is a recurring source of "Glific returned a generic error" bugs (2026-05-19 FeedbackConsumer.send_glific_notification shipped passing Student.name as contact_id; bug took 2 hours to debug).

    Identifier Type Example Lives on
    Frappe Student doc name string "ST00051238" Student.name, PE.student
    Glific contact ID numeric string "13325" Student.glific_id, PE.glific_id, Glific contactByPhone result
    Phone (Glific-stored) E.164-ish "91XXXXXXXXXX" Student.phone, Glific contact's .phone
    Frappe Batch doc name string "palv2-test-BT52231" Batch.name, PE.batch
    Friendly batch identifier short string "SP_BATCH_01" Batch.batch_id, Glific batch_id contact field

    Hard rules

    1. Any function whose signature includes contact_id, glific_id, student_id, batch, or batch_id must document in its docstring exactly which of these identifier types it expects.
    2. When crossing between systems (Glific ↔ Frappe), explicitly resolve the identifier at the call site rather than passing it through opaquely.
    3. Any call to a Glific API helper (start_contact_flow, update_contact_fields, add_contact_to_group, remove_contact_from_group) must visibly resolve the Glific contact ID at the call site — not via a variable named student_id whose origin is ambiguous.

    Wrong pattern

    def send_glific_notification(self, message_data):
    student_id = message_data.get("student_id")   # actually a Frappe doc name
    start_contact_flow(
        flow_id=flow_id,
        contact_id=student_id,   # ← Glific can't resolve "ST00051238"
        default_results=...,
    )

    Right pattern

    def send_glific_notification(self, message_data):
    student_id = message_data.get("student_id")   # Frappe Student doc name
    glific_id = frappe.db.get_value("Student", student_id, "glific_id")
    if not glific_id:
        frappe.logger().warning(
            f"Student {student_id} has no glific_id; "
            f"skipping notification for submission {submission_id}"
        )
        return
    start_contact_flow(
        flow_id=str(flow_id),
        contact_id=str(glific_id),   # ← visibly resolved at the call site
        default_results=...,
    )

    Code-reviewer rule

    When reviewing any call to a Glific API helper, ask: "where did the contact_id come from?" If the answer is "a parameter that flowed in from a few functions ago" — flag it as Major. The variable name student_id is opaque about which kind of ID it carries; trace it to its origin or require an explicit resolution at the call site.

    Realtime updates

    frappe.publish_realtime("event_name", {"payload": 1}, user=self.owner) pushes a SocketIO event the JS form listens for. Useful for "your certificate is ready" type pings.

    State-machine controllers — project idioms

    For controllers that mutate a state-machine doc (ProgramEnrollment and friends), three patterns are non-negotiable on this project. They live canonically in .claude/memory/patterns.md:

    Atomic claim with journey_label guard (P-001)

    Every state-changing UPDATE goes through a WHERE journey_label = expected_label … RETURNING name query. 0 rows returned = parallel handler already moved the state; skip without raising.

    claimed = frappe.db.sql("""
    UPDATE "tabProgramEnrollment"
       SET resolved_flow_state = %s, journey_label = %s,
           next_action_at = %s,    next_action_type = %s
     WHERE name = %s AND journey_label = %s
     RETURNING name
""", (new_state, new_label, next_at, next_type, pe_name, expected_label))
if not claimed:
    return

    Never use SELECT ROW_COUNT() to count affected rows — Postgres doesn't have it (lesson L-001). Use len(claimed) or if not claimed:.

    COALESCE-update for race-tolerant counters (P-002)

    Counters that race against resets (weekly point counters reset by T14, etc.) MUST use a single atomic UPDATE with COALESCE, never read-then-write:

    # Bad — read-then-write loses races
pe = frappe.get_doc("Program Enrollment", pe_name)
pe.weekly_quiz_points += earned
pe.save()

# Good — atomic at the column level
frappe.db.sql("""
    UPDATE "tabProgramEnrollment"
       SET weekly_quiz_points = COALESCE(weekly_quiz_points, 0) + %s
     WHERE name = %s
""", (earned, pe_name))

    Lesson L-011.

    The wider rule — doc.save(ignore_permissions=True) is a write-every-column hazard

    pe.save(ignore_permissions=True) writes the FULL row from the in-memory doc. Any column another path bumped via atomic SQL between frappe.get_doc("PE", name) and this .save() gets silently overwritten with the stale value the in-memory doc has been carrying. The longer the request/handler, the wider the race window.

    This isn't theoretical: the TAP LMS PE doctype has 40+ columns; ~10 of them (the total_* and weekly_* points columns plus the streak/gems pair) get bumped concurrently by activity_points / quiz_points / feedback hook handlers. Every pe.save() in a code path that doesn't intend to mutate ALL columns is a potential drift source. During the 2026-05-26 pre-launch sweep we found 11 such sites (7 in flow_callback.py, 3 in pe_dispatcher.py, 1 T25 in state_machine.py) and replaced them with targeted db.set_value({...changed fields only...}) + pe.reload().

    # WRONG — writes every PE column from a possibly-stale in-memory doc
pe = frappe.get_doc("ProgramEnrollment", pe_name)
# ... long handler runs; another worker bumps total_points concurrently ...
pe.next_action_at = some_new_time
pe.next_action_type = "escalation"
pe.save(ignore_permissions=True)   # ← clobbers the concurrent total_points bump

# RIGHT — atomic, only touches the columns this handler owns
frappe.db.set_value(
    "ProgramEnrollment", pe_name,
    {"next_action_at": some_new_time, "next_action_type": "escalation"},
    update_modified=False,
)
pe.reload()    # if downstream code in this handler needs to read pe fields

    Rule of thumb for PE-like doctypes with concurrent column writers: handlers that intend to write 1–3 specific fields use db.set_value; handlers that intend to bulk-reset the whole row (dev_tools.reset_pe_to_state_0) keep pe.save() because the intent IS to clobber. The signal is the verb: "set N specific things" vs "rewrite the whole doc to a known state."

    db.set_value bypasses controller validate AND on_update AND track_changes — this is the standard Frappe behavior. It's a deliberate trade: the gain is no-clobber semantics; the cost is no automatic save-hook side effects. If the column being set is Glific-mirrored, follow up with dev_tools.reconcile_pe_to_glific(pe_name) (or _enqueue_contact_field_sync(pe)) to push the change. If the column requires validate-style guarding, do the validation manually before calling set_value.

    Audit-field-first idempotency (P-005)

    Per-attempt audit fields (e.g., StudentQuizAttempt.points_earned) should be written FIRST, before any rollup updates. The field is the lock — re-runs check if attempt.points_earned: return.

    def award_points(attempt_name):
    attempt = frappe.get_doc("Student Quiz Attempt", attempt_name)
    if attempt.points_earned:
        return                     # ← write-once lock; re-runs are no-op
    earned = compute(...)
    frappe.db.set_value("Student Quiz Attempt", attempt_name, "points_earned", earned)
    apply_to_pe_counters(earned)   # safe to retry from here

    Lesson L-012.

    Common anti-patterns

    • Putting business rules in before_save instead of validate — they don't run during db_update calls and you get inconsistent behavior.
    • Using frappe.db.set_value to flip a status field that has its own controller logic, then being surprised the side effects didn't fire.
    • Querying inside a loop (for x in ...: frappe.get_doc(...)) — fetch once with frappe.get_all and a name in (...) filter.
    • Forgetting _() on strings, then having the translation team chase you.
    • Calling frappe.db.commit() in the middle of on_submit — partial state if the rest of the method throws.
    • Wrapping a state-changing UPDATE in a broad except Exception: block with a "MariaDB fallback" branch. The except swallows real PG errors, the fallback is dead code on this project, and the combination risks double-running. Lesson L-007 — remove rather than maintain.

    When the controller is too small for its own file

    Generic helpers (e.g., a function used by many DocTypes) belong in app/<your_app>/<your_module>/utils.py or a dedicated module — not duplicated across controllers. Import explicitly; don't rely on Frappe's monkey patching.
