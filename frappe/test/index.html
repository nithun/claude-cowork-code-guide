    Frappe testing skill

    Frappe ships a unittest-based test runner that bootstraps a fully working site, runs your tests inside a transaction, and rolls back at the end. That last bit is what makes Frappe testing pleasant — every test starts from a clean DB.

    Tests are part of the feature, not a follow-up

    This rule has been violated three times running. Codified now to stop the bleeding (L-025).

    Hard rule: a function that touches Glific (start_contact_flow, start_group_flow, update_contact_fields), RabbitMQ (publish, consume), Google Cloud Storage, the database via raw SQL or frappe.db.set_value, or shared scheduler / cron state MUST ship with at least one test in the same commit as the function. Filing the test as a follow-up task (#21, #41, #53, …) is not acceptable. The bug always lands before the follow-up does, every time.

    This applies to feature-builder handoffs and to code-reviewer's blocking criteria. See .claude/agents/feature-builder.md workflow step "After you finish" and .claude/agents/code-reviewer.md test-coverage section.

    What category of test applies — 5-line decision tree

    1. Touches Glific or RabbitMQ or GCS? → unittest.mock mock + assert call shape AND a fault-injection test that raises and asserts retry/DLQ behavior (L-015).
    2. Atomic-claim or COALESCE-update SQL (P-001 / P-002)? → concurrency/race test calling the handler twice and asserting only one side-effect (L-018).
    3. Scheduler tick / cron path? → time-controlled test that runs the tick with frozen frappe.utils.now_datetime() and asserts dispatch idempotency.
    4. Whitelisted endpoint? → happy-path + validation-error + permission test (L-016).
    5. Pure CRUD on own DocType? → one happy-path test is enough; no race or mock needed.

    If the function fits more than one row, it needs tests from each row.

    Recurrence: missing_tests_on_new_api appeared 3x in .claude/memory/code-review-findings.jsonl (commits fca37df, 875d6d6, post-875d6d6). Commit 875d6d6 shipped 10+ new functions (pe_dispatcher 565 lines, 8 handlers, plus feedback_consumer_hook, _seed_pe_actions, check_auto_activate, staggered_action_time) with zero tests. The fix-up commit added 10 tests but left 5 handlers uncovered. The cost is one more BLOCKING review per missed function.

    Before moving / refactoring an existing function — check its failure history

    Beyond the test-coverage checklist for new code, refactors of existing code need a pre-flight check. The pattern that hit us during the 2026-05-28 journey/ → summer_program/ migration: a function had silently-swallowed exceptions for days; the queue diagnostic showed 5 historical failures; the move was performed without investigating; the bug would have followed the file to the new location.

    Hard rule for refactors that relocate or rename a function: before declaring the move "safe," grep its failure history:

    # After loading sp_console (see skills/frappe-bench/SKILL.md console section):
queue_failures_for("the_function_name")

    Plus the Error Log doctype:

    import frappe; frappe.db.rollback()
frappe.db.sql("""
    SELECT method, creation, LEFT(error::text, 200) AS excerpt
      FROM "tabError Log"
     WHERE error::text LIKE %s
     ORDER BY creation DESC LIMIT 20
""", ("%the_function_name%",), as_dict=True)

    If either query returns hits, the move becomes a refactor: fix the root cause inline (the fix-pattern usually already exists elsewhere in the codebase) BEFORE relocating the code. Don't migrate broken code unchanged; you'll ship the same bug to a new location and a reviewer will catch it later anyway.

    This was L-057-proposed in the 2026-05-26 housekeeping retrospective.

    Where tests live

    app/<your_app>/<your_module>/doctype/course_enrollment/test_course_enrollment.py
app/<your_app>/<your_module>/tests/test_<feature>.py

    The test_ prefix is required — that's how the runner discovers them. One test file per DocType is conventional; cross-cutting features get their own tests/ folder.

    Anatomy

    import frappe
import unittest

class TestCourseEnrollment(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        # Runs once before any test in this class. Use to seed reference data
        # the whole class shares. Not rolled back automatically — clean up in tearDownClass.
        cls.student = make_student("STU-TEST-001")
        cls.course = make_course("CS-TEST-101")

    def setUp(self):
        # Runs before each test. Frappe wraps each test in a transaction
        # that's rolled back, so most setUp work is unneeded.
        pass

    def test_creates_enrollment(self):
        doc = frappe.get_doc({
            "doctype": "Course Enrollment",
            "student": self.student,
            "course": self.course,
        }).insert()
        self.assertEqual(doc.status, "Active")
        self.assertTrue(frappe.db.exists("Course Enrollment", doc.name))

    def test_blocks_duplicate_enrollment(self):
        frappe.get_doc({
            "doctype": "Course Enrollment",
            "student": self.student,
            "course": self.course,
        }).insert()
        with self.assertRaises(frappe.ValidationError):
            frappe.get_doc({
                "doctype": "Course Enrollment",
                "student": self.student,
                "course": self.course,
            }).insert()

    @classmethod
    def tearDownClass(cls):
        # Clean up class-level seed data.
        for name in frappe.get_all("Course Enrollment", filters={"student": cls.student}, pluck="name"):
            frappe.delete_doc("Course Enrollment", name, force=True)

    Running tests

    # All tests in your app
bench --site <site> run-tests --app tap_lms

# Single module
bench --site <site> run-tests --module tap_lms.tap_lms.doctype.course_enrollment.test_course_enrollment

# Single test
bench --site <site> run-tests --test tap_lms.tap_lms.doctype.course_enrollment.test_course_enrollment.TestCourseEnrollment.test_blocks_duplicate_enrollment

# With coverage
bench --site <site> run-tests --app tap_lms --coverage

    Pass --profile to get per-test timing.

    Frappe's quality-of-life helpers

    frappe.tests.utils.FrappeTestCase (subclass instead of unittest.TestCase) gives you:

    • self.assertDocumentEqual(expected_dict, doc) — compares meaningful fields.
    • Automatic transaction wrapping with rollback on every test.
    • A self.client for HTTP-style calls into your whitelisted methods.
    from frappe.tests.utils import FrappeTestCase

class TestEnrollAPI(FrappeTestCase):
    def test_enroll_endpoint(self):
        result = frappe.call("tap_lms.api.enroll", student="STU-001", course="CS101")
        self.assertTrue(result["created"])

    Project test factories — use these, don't reinvent

    The Summer Program has a canonical factory module at app/tap_lms/summer_program/tests/factories.py exposing:

    • make_batch(label, batch_id, ...) — populates EVERY mandatory field on the Batch doctype (start_date, end_date, regist_start_date, regist_end_date, batch_id, program_type, total_weeks, current_calendar_week, grace_window_days). Pass label (unique per test) and batch_id (the friendly identifier, distinct from the doc name).
    • make_student(suffix, phone_prefix, glific_id, ...) — populates name1, phone, glific_id, archetype, experiment_arm, language. Each test file should use a unique phone_prefix to keep its students in a disjoint phone space.
    • make_active_pe(student_id, batch_name, glific_id) — directly inserts a minimal active PE without running _process_pe_chunk. Useful for setting up pre-conditions like "sibling A is already enrolled."

    Why this exists

    Each test file inventing its own _ensure_batch() is the recurring mandatory_field_missing pattern (4× recurrence between 2026-05-16 and 2026-05-19). The Batch doctype gained regist_end_date as mandatory at some point; test files written before that change kept passing while new ones written without checking the doctype's mandatory list failed at setUpClass time.

    When the doctype gains a new mandatory field, update factories.py once — every test that imports the factory inherits the fix. Test files that inline their own fixture have to be patched individually and inevitably one gets missed.

    Usage pattern

    from tap_lms.summer_program.tests.factories import (
    make_batch, make_student, make_active_pe,
)

class TestMyFeature(FrappeTestCase):
    @classmethod
    def setUpClass(cls):
        super().setUpClass()
        cls.batch = make_batch("MyFeatureTestBatch", batch_id="MF01")

    def test_something(self):
        student = make_student(
            suffix="01",
            phone_prefix="+9999800",   # unique-per-test prefix
            glific_id="glific-mf-01",
        )
        pe = make_active_pe(student, self.batch, glific_id="glific-mf-01")
        # ... assertions

    Hard rule

    Do not redefine _ensure_batch / _ensure_student / _ensure_pe in new test files. Import from factories.py. The reviewer treats local fixture inlining as a Major finding when the factory covers the case.

    If you genuinely need a different fixture shape (e.g. a Batch with a specific program_type value the factory doesn't expose), pass it as a kwarg to the factory. If the factory doesn't accept that kwarg, ADD IT to the factory rather than inline a one-off.

    Generic test data factories (for new modules without their own)

    Don't paste DocType creation everywhere — write factories.

    # app/<your_app>/tests/factories.py
import frappe

def make_student(student_id="STU-AUTO", **overrides):
    if frappe.db.exists("Student", student_id):
        return student_id
    return frappe.get_doc({
        "doctype": "Student",
        "student_id": student_id,
        "first_name": overrides.get("first_name", "Test"),
        "last_name": overrides.get("last_name", "Student"),
        "email": overrides.get("email", f"{student_id.lower()}@test.local"),
    }).insert(ignore_permissions=True).name

def make_course(code="CS-AUTO", **overrides):
    if frappe.db.exists("Course", code):
        return code
    return frappe.get_doc({
        "doctype": "Course",
        "course_code": code,
        "title": overrides.get("title", f"Test Course {code}"),
        "credits": overrides.get("credits", 3),
    }).insert(ignore_permissions=True).name

    User context

    Tests run as Administrator by default. To exercise permission logic:

    def test_student_cannot_delete_enrollment(self):
    frappe.set_user("student@test.local")
    try:
        with self.assertRaises(frappe.PermissionError):
            frappe.delete_doc("Course Enrollment", self.enrollment)
    finally:
        frappe.set_user("Administrator")

    Always restore Administrator in finally — leaks bleed across tests.

    Mocking external services

    Frappe doesn't bundle a mocking library — use unittest.mock:

    from unittest.mock import patch

def test_webhook_calls_payment_provider(self):
    with patch("tap_lms.tap_lms.payments.requests.post") as fake_post:
        fake_post.return_value.status_code = 200
        fake_post.return_value.json.return_value = {"ok": True}
        # ... call the code that hits the provider
        fake_post.assert_called_once()

    For email, set frappe.flags.in_test = True (the test runner does this automatically) — emails are queued, not sent.

    For background jobs, in tests they run synchronously by default unless frappe.flags.now = True is overridden. To assert a job was enqueued without running it, patch frappe.enqueue.

    What about pytest?

    Frappe v15+ has experimental pytest support via pytest-frappe. The wins are richer fixtures, parallelism, and parameterization. The cost is one more dependency and slightly different conventions. Decision is yours; the unittest runner is fine for most cases. If you adopt pytest, fixtures replace setUpClass:

    import pytest

@pytest.fixture
def student():
    return make_student("STU-PYTEST")

def test_enrollment_creates_progress(student):
    ...

    CI integration

    A minimal GitHub Actions step:

    - name: Set up bench (Postgres)
  run: |
    pip install frappe-bench
    bench init --frappe-branch version-15 frappe-bench --skip-redis-config-generation --skip-assets
    cd frappe-bench
    bench new-site test_site --db-type postgres --db-host 127.0.0.1 --admin-password admin
    bench --site test_site install-app tap_lms

- name: Run tests
  working-directory: frappe-bench
  run: bench --site test_site run-tests --app tap_lms --coverage

    Pin the Frappe branch and Postgres version. Test environments diverging from prod is the leading cause of "passes locally, fails in CI."

    Common gotchas

    • A test that calls frappe.db.commit() will break the rollback contract — every later test in the run sees the leaked data. Don't commit in tests.
    • A test that mutates the metadata cache (frappe.clear_cache() then loads new DocTypes) bleeds across tests. Reset what you mutate in tearDown.
    • Permission tests that don't restore the user (see above) cause "but it works on my machine" debugging hell.
    • Tests that assume autoincrement names (CRS-00001) are brittle — name your test fixtures explicitly.
    • Long test setup that creates 50 docs to test one thing — extract a factory; you'll thank yourself.

    When a feature ships

    Aim for: one happy path, one validation/edge-case, one permission test per public-facing controller method or whitelisted API. That's the minimum bar for "this is reviewed and tested" — anything less, the code-reviewer agent will flag (lesson L-016).

    Project-specific test rules

    These rules come from real bugs that shipped and are non-negotiable:

    • Never call frappe.db.commit() in tests. The runner relies on transaction rollback for isolation. A single commit leaks data into every later test in the run. Lesson L-017. Code-reviewer flags this as BLOCKING.
    • Atomic-claim code needs an actual concurrency test. A SELECT ROW_COUNT() style PG-incompatibility bug cannot be caught by code review alone — it surfaces only when a duplicate UPDATE runs and the code can't tell the difference. Every state-changing UPDATE that uses pattern P-001 needs a test that:
    • Sets the doc to expected_label.
    • Calls the handler twice in the same test (or from two threads) and asserts the second call is a no-op (no double-side-effects, no exception).
    • Asserts the row's journey_label advanced exactly once.

    Lesson L-018. Without this test, the bug ships. - Restore Administrator after permission tests. Always wrap frappe.set_user(...) in try/finally — leaks bleed across tests in the same run.
