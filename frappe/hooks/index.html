    Frappe hooks.py skill

    hooks.py lives at app/<your_app>/hooks.py and is the single declarative configuration file Frappe reads at startup. Every "react to X happening anywhere in the system" extension goes here.

    When hooks vs. when controllers

    Use a controller method (<doctype>.py lifecycle hook) when reacting to events on your own DocType. The controller is the home for that doc's logic.

    Use hooks.py doc_events when reacting to events on a DocType you don't own — typically a core ERPNext DocType (User, Customer, Sales Invoice) or one from another app. You can't edit their controllers, so you register a callback in hooks.py.

    doc_events

    doc_events = {
    "User": {
        "after_insert": "tap_lms.tap_lms.user_hooks.create_student_profile",
    },
    "Sales Invoice": {
        "on_submit": [
            "tap_lms.tap_lms.billing_hooks.activate_paid_enrollments",
            "tap_lms.tap_lms.billing_hooks.send_receipt",
        ],
    },
    "*": {
        "before_save": "tap_lms.tap_lms.audit.stamp_modified_by_ip",
    },
}

    Each value is a dotted import path to a function. Signature: def handler(doc, method=None): where doc is the document and method is the event name (useful when one function listens to multiple events).

    "*" matches every DocType. Use sparingly — it runs on every save in the system.

    Scheduler events

    scheduler_events = {
    "all":     ["tap_lms.tap_lms.scheduled.heartbeat"],         # every ~4 minutes
    "hourly":  ["tap_lms.tap_lms.scheduled.refresh_summaries"],
    "daily":   ["tap_lms.tap_lms.scheduled.expire_lapsed_enrollments"],
    "weekly":  ["tap_lms.tap_lms.scheduled.send_weekly_digest"],
    "monthly": ["tap_lms.tap_lms.scheduled.archive_old_attempts"],
    "cron": {
        "0 2 * * *": ["tap_lms.tap_lms.scheduled.nightly_sync"],
    },
}

    cron keys take standard 5-field crontab expressions. Functions take no arguments. Errors are logged to the Error Log DocType; they don't kill the scheduler.

    For the scheduler to actually run, the bench daemon must be up. In dev: bench start. In prod: supervisor should be running bench schedule and bench worker --queue default,short,long.

    Critical: changes to scheduler_events require bench migrate, not just bench restart. Frappe stores scheduler entries in the tabScheduled Job Type table; that table is populated from hooks.scheduler_events only by migrate. A new cron entry added to hooks.py after restart-only deploys is invisible to the scheduler — the function never fires. Verify with:

    import frappe; frappe.db.rollback()
frappe.db.sql("""
    SELECT method, cron_format, stopped FROM "tabScheduled Job Type"
     WHERE method LIKE 'your_app.your_module.%' ORDER BY method
""", as_dict=True)

    This contrasts with doc_events, override_doctype_class, and other hooks.py keys that take effect on bench restart alone because they're read at code-import time.

    Background jobs via frappe.enqueue — the silent-success failure mode

    Functions you call with frappe.enqueue(method_path, queue="short", **kwargs) run in RQ workers. Two things to know:

    1. Queues and priorities. Standard queues are short (high priority, jobs < ~30s), default (medium), long (low, multi-minute). Workers typically poll multiple queues; short jobs interleave fastest. Use short for per-user-event work (Glific sync, content-log inserts) and long for slow API calls (Vocallabs, AI feedback).

    2. The silent-success failure mode. RQ marks a job as failed only if it raises an exception. A job that catches an exception and returns normally is marked finished — the FailedJobRegistry stays empty, queue-depth alerts stay silent, but the work the job was supposed to do never happened.

    # WRONG — looks "finished" to RQ even when the insert fails
def my_job(student_id, content_id, ...):
    try:
        log.insert(ignore_permissions=True)
        frappe.db.commit()
    except Exception as e:
        frappe.log_error(f"job failed: {e}", "My App")
        # implicit return None → RQ thinks the job succeeded

# RIGHT — fails loudly so RQ + FailedJobRegistry + ops see it
def my_job(student_id, content_id, ...):
    try:
        log.insert(ignore_permissions=True)
        frappe.db.commit()
    except Exception as e:
        try:
            frappe.db.rollback()    # L-030: clears poisoned txn so log_error works
        except Exception:
            pass
        try:
            frappe.log_error(
                f"my_job failed: {e}\nstudent={student_id} content={content_id}",
                "My App",
            )
        except Exception:
            frappe.logger().error(f"my_job failed (log_error also failed): {e}")
        raise   # ← critical: marks the job FAILED in RQ

    Two corollaries: - Rollback before log_error. Postgres aborts the whole transaction on the first failed statement; frappe.log_error does its own SELECT and would fail with InFailedSqlTransaction without the rollback. The nested try/except around log_error itself is a defense against double-fault when the Error Log doctype meta lookup also fails. - Pair the raise with retry+DLQ if the job is idempotent. Pattern P-007: enqueue the job again with retry_count + 1 until a MAX_RETRIES budget is exhausted, then write a structured DLQ Error Log entry for manual replay. state_machine._sync_contact_fields_job is the canonical implementation.

    Before moving / renaming an existing background job, search its failure history first:

    # After loading sp_console (see skills/frappe-bench/SKILL.md console section):
queue_failures_for("the_func_name")

    If there are hits, fix the root cause inline before relocating. A function being moved usually triggers a code review; a silent-failure bug being moved unchanged turns into a launch-week incident.

    fixtures

    Fixtures are records exported as JSON and re-imported on bench migrate — used for Roles, Custom Fields, Property Setters, Workflows, Print Formats, anything you want to ship as part of the app.

    fixtures = [
    {"dt": "Custom Field", "filters": [["dt", "in", ["User", "Customer"]]]},
    {"dt": "Property Setter", "filters": [["doc_type", "in", ["User", "Customer"]]]},
    {"dt": "Role", "filters": [["name", "in", ["TAP Instructor", "TAP Student"]]]},
    "Workflow",
    "Workflow State",
    "Workflow Action Master",
]

    Export with bench --site <site> export-fixtures. The JSON files land in app/<your_app>/fixtures/. Commit them.

    JS / CSS includes

    # Loaded on every desk page
app_include_js = ["/assets/tap_lms/js/desk.bundle.js"]
app_include_css = ["/assets/tap_lms/css/desk.bundle.css"]

# Loaded on every portal/web page
web_include_js = ["/assets/tap_lms/js/portal.bundle.js"]
web_include_css = ["/assets/tap_lms/css/portal.bundle.css"]

# Loaded only on a specific DocType's form (alternative to a sibling .js file)
doctype_js = {"Sales Invoice": "public/js/sales_invoice_overrides.js"}
doctype_list_js = {"Sales Invoice": "public/js/sales_invoice_list.js"}

    For bundled assets, drop .bundle.js files in public/js/ and Frappe's esbuild step picks them up on bench build.

    Override classes (the nuclear option)

    override_doctype_class = {
    "Sales Invoice": "tap_lms.tap_lms.overrides.sales_invoice.CustomSalesInvoice",
}

    The override class subclasses the original. Use only when you need to change behavior the original doesn't expose via lifecycle hooks. Test it on every Frappe upgrade — overrides are the most upgrade-fragile thing in hooks.py.

    override_whitelisted_methods = {
    "frappe.www.contact.send_message": "tap_lms.tap_lms.overrides.contact.send_message",
}

    Permission queries (row-level filtering)

    permission_query_conditions = {
    "Course Enrollment": "tap_lms.tap_lms.permissions.enrollment_query",
}

has_permission = {
    "Course Enrollment": "tap_lms.tap_lms.permissions.enrollment_has_permission",
}

    The query function returns a SQL fragment Frappe AND's into list queries. The has_permission function returns a bool for individual doc access.

    def enrollment_query(user):
    if "TAP Admin" in frappe.get_roles(user): return ""
    return f"`tabCourse Enrollment`.owner = {frappe.db.escape(user)}"

    (That backtick syntax is the one place Frappe's translator handles for you. On Postgres it becomes "tabCourse Enrollment".owner.)

    Install / migrate / uninstall lifecycle

    before_install = "tap_lms.install.before_install"
after_install = "tap_lms.install.after_install"
after_migrate = ["tap_lms.install.create_default_roles"]
before_uninstall = "tap_lms.install.cleanup"

    after_install runs once per site when the app is first installed; after_migrate runs on every bench migrate. Idempotency matters — wrap in if not frappe.db.exists(...).

    Patches

    Schema changes that need data migration go in patches.txt (one dotted path per line) and the patch lives at app/<your_app>/patches/<version>/<name>.py with an execute() function. Patches run in order, each only once. Use them whenever you rename fields, change types non-trivially, or backfill data.

    Email and notifications

    notification_config = "tap_lms.notifications.get_notification_config"

    The function returns a dict that drives the bell-icon notifications in the desk. Useful for "you have N pending grading items" indicators.

    Boot session

    boot_session = "tap_lms.boot.boot_session"

    Inject keys into the JS frappe.boot object that's available on every page. Useful for global config the front-end needs (feature flags, branding).

    What NOT to put in hooks.py

    • Long imports at module level — hooks.py is read on every request indirectly via the metadata cache. Keep it dependency-light.
    • Complex logic — it's a config file. Functions belong elsewhere; hooks.py only references their dotted paths.
    • Conditional blocks based on environment — Frappe doesn't reload hooks.py on env changes; you'll surprise yourself. Use frappe.conf.get(...) inside the called functions instead.

    After editing hooks.py

    Hooks are cached. After changes:

    bench --site <site> clear-cache
bench restart   # or `bench start` in dev

    Without this, your new doc_events / scheduler entries won't fire and you'll spend an hour blaming the wrong code.
