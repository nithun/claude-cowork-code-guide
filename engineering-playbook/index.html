    Engineering playbook — CR → build → release

    For engineers. You live in Claude Code (the build half). You build from named documents, not from chat — a tasks file, a CR, or a BR. This page walks the loop from "there's a spec" to "it's released."

    What you build from

    Inbound Source of truth Start with
    New feature (from a PRD) docs/.../*-tasks.md (task-manager's output) "Implement TASK-NNN"
    Behavior change docs/change-requests/CR-NNN-*.md "Implement CR-NNN"
    Non-trivial bug docs/bug-reports/BR-NNN-*.md (+ tasks) "Implement the BR-NNN fix"
    Refactor / one-shot tech work a direct task just describe it

    The CR gate: if a CR is still Status: Proposed, feature-builder will stop and ask. Never build against a draft — wait for the approver to flip it to Approved (after which the body is immutable).

    1. Write the change request (for behavior changes)

    If you're changing how an existing feature works, the change starts as a CR, not code:

    "Write a CR for: drop students at end of grace instead of pausing."

    change-requirement interviews you and writes CR-NNN with the required sections: Motivation, Current Behavior, Proposed Behavior, Scope, Migration, Edge Cases, Acceptance Criteria, Test Plan, Rollback. If it touches schema or system topology, it pulls in architecture-reviewer. The approver flips it to Approved — now it's the build's source of truth.

    2. Build it

    "Implement CR-NNN" (or "Implement TASK-NNN")

    feature-builder reads memory + the CR/PRD + the relevant skills, then builds top-down (data model → logic → API → tests). Two rules it won't break:

    • Tests ship in the same commit as any function with a side effect. No "I'll add tests later."
    • ADR gate: if the work surfaces an un-made architecture decision (new external service, new scheduling cadence, new perf constraint), it stops and spawns architecture-reviewer before continuing.

    It ends with a handoff: files changed, acceptance-criteria status, the exact commands to run, and a deploy checklist generated from what the diff touched.

    3. Review + test (runs for you)

    After a build, the policy is to spawn code-reviewer and test-runner in parallel automatically (trivial edits skip them, and Claude says so). You can also call them by hand:

    "Review the diff" · "Run tests"

    code-reviewer checks correctness, security, idioms, and that every acceptance criterion has a covering test. test-runner runs the suite and files a task per failure. Recurring findings escalate to the retrospective agent, which turns them into rules so the same mistake doesn't return.

    Don't release until review is clean and tests are green.

    4. Release

    The build loop is automated; release is deliberately manual — a human runs the deploy. The steady-state loop for most services:

    review clean + tests green
      ↓
merge / push to the deploy branch
      ↓
run migrations (if any)
      ↓
deploy / restart the service
      ↓
smoke-test the change in the running env
      ↓
watch logs / errors for a short window

    Generic release checklist:

    • [ ] Review clean, tests green on the target branch.
    • [ ] Migrations are idempotent and run cleanly on a fresh DB.
    • [ ] Config / secrets / feature flags the change needs are in place.
    • [ ] A rollback path exists (previous build + DB backup) and you know the trigger.
    • [ ] Post-deploy smoke test passes against the running env.
    • [ ] Error/queue volume watched for a window after cutover.

    TAP LMS release specifics

    TAP LMS adds two wrinkles — read these before deploying TAP:

    • Two-folder sync (L-024): you edit app/ in this folder; the bench at ~/frappe-bench/apps/tap_lms is what Frappe runs. Flow: edit here → copy to bench → commit + push from bench → pull back so this folder stays current. Never re-copy files into the bench after the bench has pulled them from git — that creates the untracked-file condition that blocks git pull.
    • The deployment runbook: the full, hard-won procedure (pre-flight probes, bench migrate, bench restart, smoke tests, rollback tree) is docs/deployment-runbook.md. Note it's written for the first-time install; a routine incremental release follows the shorter loop above (copy → commit/push → bench migrate → bench restart → smoke test), using the runbook's smoke-test and rollback sections.
    • migrate vs restart: bench migrate syncs schema + scheduler jobs; bench restart reloads code. Some changes need both — the build handoff's deploy checklist tells you which.

    5. Publish the docs (if changed)

    If the change updates published docs, see Publishing.

    6. Close the loop

    After a meaningful chunk of work — especially if review caught something — run:

    "Run retrospective"

    It reads recent reviews, test failures, and git history, and proposes (or, in closed-loop mode, applies) edits to skills/agents/memory so the next build is more correct. This is the part that compounds.

    Your phrasebook

    • "Write a CR for …" — scope a behavior change → change-requirement
    • "Implement CR-NNN" / "Implement TASK-NNN" — build it → feature-builder
    • "Review the diff" / "Review the last N commits" → code-reviewer
    • "Run tests" / "did I break anything" → test-runner
    • "Does our architecture support …" → architecture-reviewer
    • "Run retrospective" — learn from the work → retrospective

    Worked example

    CR-012: certificate is re-issued every time the completion endpoint is hit (should be once).

    1. "Implement CR-012." feature-builder reads the CR, restates scope, lists files, adds an idempotency guard + a test asserting a second call doesn't re-issue — same commit.
    2. code-reviewer + test-runner run: review clean, tests green.
    3. Release: copy to bench, commit/push, bench migrate (no schema change here, so really just bench restart), smoke-test the endpoint twice, confirm one certificate.
    4. "Run retrospective" — if the bug class (missing idempotency) has recurred, it becomes a rule.
