    Adopt it for a new project

    You're starting a new TAP feature in its own repo, or a brand-new microservice (FastAPI, Node, a data pipeline). This page shows how to stand up the Cowork + Claude Code system there.

    The model: bootstrap fresh, don't fork

    Do not copy claude-cowork-code into your new repo. Most of what's here is TAP-LMS-specific — the frappe-* skills, the Frappe/Postgres rules baked into feature-builder / code-reviewer / test-runner, the accumulated lessons. Dragging those into a FastAPI service is pure noise.

    Instead, run four bootstrap prompts in your new repo. They make Claude Code discover your stack and generate an agent layer that fits it. The methodology comes over; the Frappe baggage doesn't. The prompts live in docs/cowork-bootstrap.md — copy them from there; this page is the orientation around them.

    Why discovery beats a template: a template bakes in assumptions (build command, test runner, language). Discovery asks. That's what makes the same four prompts work for a Frappe app, a FastAPI service, and a Node API without edits.

    Before you start — three decisions

    Prompt 0 will ask you these. Decide in advance:

    Decision Recommended default Why
    Where is the agent layer tracked? Inside the new code repo Simplest. Use a separate repo only if the code repo must stay deployable/clean.
    Self-improvement autonomy Proposal-only for ~the first month The retrospective suggests memory/agent edits; you apply the good ones. Graduate to closed-loop once proposals are consistently good.
    Which agents The full 8 only if the project warrants it A small service can start with feature-builder + code-reviewer + test-runner + retrospective and add prd-author / change-requirement / architecture-reviewer / task-manager when the planning load shows up.

    The four prompts

    Open Claude Code in the new repo and paste them in order, waiting for each to finish.

    # Prompt What it does Writes anything?
    0 Discovery Inspects stack, build/test commands, git root, any existing .claude/, and whether code runs from a separate location (symlink needed?). Then proposes a plan and asks the three decisions above. No — read-only
    1 Scaffold Creates CLAUDE.md, WORKFLOW.md, .claude/agents/ (each with an ## INVARIANTS (do not edit) fence), and .claude/memory/ (lessons, patterns, circuit-breaker, empty logs). Uses the build/test commands it discovered. Yes — commits the layer
    2 Retrospective agent Adds .claude/agents/retrospective.md in proposal-only mode, with its own INVARIANTS (it can never weaken them, even on itself). Yes
    3 Seed + verify Drafts initial lessons from your git history (you approve), then dry-runs the retrospective in report-only mode and verifies the whole setup. Proposes, then applies what you confirm

    What you get

    After the four prompts your new repo has:

    your-service/
├── CLAUDE.md            ← project context: YOUR stack, build/test commands, conventions
├── WORKFLOW.md          ← the path-per-task-type map, same shape as TAP's
├── .claude/
│   ├── agents/          ← agents generated for YOUR stack
│   └── memory/          ← lessons.md, patterns.md, circuit-breaker.json, *.jsonl
└── (your code)

    No skills/frappe-*, no TAP lessons — a clean layer that knows your build and test commands.

    What carries over vs. what gets regenerated

    Carries over near-verbatim Regenerated for your stack
    prd-author — writing PRDs/BRs is stack-agnostic feature-builder — knows your language, framework, test idioms
    change-requirement — CR scoping is universal code-reviewer — checks your stack's footguns (not Postgres/Frappe)
    architecture-reviewer — the COMPATIBLE / MINOR / ADR verdict model test-runner — runs your test command
    task-manager — decomposition is universal skills/ — written for your stack (e.g. fastapi-*, pytest) instead of frappe-*
    retrospective — the learning loop itself .claude/memory/ — your project's lessons, seeded from your history
    The two-tool rule + file-handoff discipline CLAUDE.md — your conventions

    The roles are the reusable asset. Their bodies are stack-specific and the bootstrap writes them fresh.

    Worked example — a FastAPI microservice

    You're building tap-notifications, a FastAPI service. After the four prompts:

    • CLAUDE.md records: Python 3.12, FastAPI, uv/pip, tests = pytest, lint = ruff, the repo layout.
    • skills/ holds something like fastapi-endpoints, pydantic-models, pytest-fixtures, sqlalchemy-migrations — not frappe-*.
    • feature-builder writes endpoints + Pydantic models + pytest tests in the same commit (the "tests in the same commit" rule carries over; the framework doesn't).
    • code-reviewer checks for FastAPI footguns (sync work in async handlers, unvalidated input) instead of Postgres-vs-MariaDB.
    • test-runner runs pytest -q.
    • prd-author, change-requirement, architecture-reviewer, task-manager, retrospective are essentially the TAP versions with the Frappe references swapped out.

    The daily loop is identical to TAP's — only the skills and the three build-loop agents differ.

    A note on memory tiers (MVP)

    The bootstrap prompts offer a two-tier memory (lessons.md for load-bearing rules + observations.md for high-churn field notes). TAP LMS deliberately started single-tier (lessons.md only) per its MVP discipline and deferred the second tier until volume justified it. Start single-tier. Add observations.md only when lessons.md is genuinely too noisy to scan. Build the minimum; let evidence pull you to more.

    Checklist

    • [ ] Prompt 0 ran read-only and you answered the three decisions.
    • [ ] Prompt 1 created CLAUDE.md, WORKFLOW.md, .claude/agents/ (each with an INVARIANTS fence), .claude/memory/.
    • [ ] Prompt 2 added retrospective in proposal-only mode.
    • [ ] Prompt 3's seeded lessons were reviewed and the dry-run looked sane.
    • [ ] The verify step confirms: build command works, test command runs, all agent files + memory files exist.
    • [ ] You can drive it: "Write a PRD for X", "Implement CR-NNN", "review the last commits", "run retrospective".

    Then open the matching playbook — product or engineering — and start shipping.
