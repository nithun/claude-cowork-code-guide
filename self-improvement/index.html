    How the system improves itself

    This is what makes the methodology more than "agents that write code." The build loop feeds a learning loop: every review finding and test failure becomes data, and a dedicated agent turns the recurring ones into rules — so the same mistake doesn't happen twice. Over time the project gets more correct on its own.

    The loop

     feature-builder ──ships──▶ code-reviewer / test-runner
                                  │  write findings + failures
                                  ▼
                     .claude/memory/*.jsonl   (append logs)
                                  │  read every run
                                  ▼
                          retrospective agent
                                  │  recurring pattern → one-line rule
                                  ▼
                  edits skills / agents / lessons.md
                                  │
                                  ▼
                       next build avoids the mistake

    The reviewers and testers don't only report to you — they log to files the retrospective reads. That file trail is what closes the loop; nothing depends on a human couriering findings around.

    When it runs — two triggers

    • Manual — you say "run retrospective". A good weekly habit, or after a rough patch.
    • Event-driven — when code-reviewer or test-runner sees the same pattern cross a threshold (≥3 occurrences), it escalates to the retrospective automatically.

    (You can also schedule it, but manual + event-driven is plenty to start.)

    What one run does

    1. Check permissions — read circuit-breaker.json: am I allowed to write right now?
    2. Read the evidence — lessons.md, patterns.md, the append logs (code-review-findings.jsonl, test-failures.jsonl, decisions.jsonl), its own past-edit log, and recent CRs / reviews.
    3. Audit itself — for each past edit, did the targeted problem actually stop? Mark it effective / neutral / ineffective.
    4. Extract patterns — promote only what clears the bar (below).
    5. Apply or propose — edit the target file (or write a proposal), one atomic commit each: retro: <what> — <why>.
    6. Log the action so the next run can audit it.

    What counts as a rule worth adding

    All four, or it's skipped:

    1. Recurs ≥3 times, or once with high consequence.
    2. Reduces to a one-line mechanical rule — "when you see X, do Y", not "be careful about X".
    3. Has a clear target file — which skill or agent should hold it.
    4. Isn't already captured (dedupe).

    What it can and can't touch

    Edits — to get smarter Never touches — human authority
    skills/* — rules, examples, anti-patterns app/ source code
    .claude/agents/* — e.g. add a check to code-reviewer architecture.md, ADRs
    lessons.md — append-and-supersede, stable IDs CRs, PRDs, bug reports, code-review reports
    CLAUDE.md — the "lessons" section only the procedural / convention sections of CLAUDE.md

    Why self-editing is safe

    • INVARIANTS fences. Every agent has a ## INVARIANTS (do not edit) block. The retrospective can rewrite agents and skills but is forbidden from touching anything inside a fence — even its own. If it thinks an invariant is wrong, it files a task for a human. It cannot remove its own guardrails.
    • Autonomy dial. Start proposal-only (it writes suggestions to docs/retrospective-runs/; you apply the good ones). Graduate to closed-loop once proposals are consistently good — then it applies directly and git is the rollback.
    • Circuit breaker. Three lanes — skills, agents, memory. A closed lane blocks all writes there until you reopen it. And the self-audit closes a lane automatically if the same edit keeps getting reverted.
    • Atomic + reversible. One edit per commit, clearly messaged, on a git-tracked tree. A bad edit is one git revert away — and the next run notices the revert and learns from it.

    How you drive it

    • Run it: "run retrospective" (or "scan for patterns").
    • Proposal-only mode: review docs/retrospective-runs/proposal-*.md and apply what you agree with.
    • Closed-loop mode: skim the retro: commits in git log; revert anything you disagree with — the system treats your revert as a signal and adjusts.

    The compounding effect is the whole point: a one-time bug becomes a permanent rule, so the curve bends toward fewer repeated mistakes the longer the project runs.
